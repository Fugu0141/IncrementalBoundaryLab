## 1. 研究背景と問い

研究対象は、ローマ字入力中の日本語・英語・コード識別子について、変換責務を逐次割り当てる方式である。
従来の文字列分割・確定・再解釈に加え、v0.6 は日本語候補の変換を Mozc へ委譲し、
Literal / Japanese / Open / Boundary を分離する。

検証すべき問い:

1. **RQ1（一次評価）**: 同一の未学習入力群に対する最終出力の CER は、比較方式より低下するか。
2. **RQ2**: 日本語と英語の責務境界の検出精度は向上するか。
3. **RQ3**: 取り消せない誤確定は減少するか。正しい確定が過剰に遅延しないか。
4. **RQ4**: 上記の改善が実用的な入力遅延、CPU・メモリ消費の範囲で達成されるか。
5. **RQ5（安全性）**: Backspace / Escape / Space / Enter / 候補選択 / フォーカス移動 / 非ASCII入力を壊さないか。

### 仮説と棄却可能性

- H1: 同一の独立評価文で、v0.6 + 実 Mozc の CER は比較対象より低い。
- H2: 正しい日本語 / Literal 境界の micro F1 が比較対象より高い。
- H3: 誤確定発生率が比較対象より低い。
- H4: 入力遅延 P95/P99 は、事前に定義した実用上の許容値を超えない。

結果が不変または悪化してもそのまま記載する。定量評価前に優位性を断定しない。

### 3.2 データセット

- まず 12–30 入力を **smoke/pilot** として人手で確認し、手順上の不具合を検出する。
- 本評価は目安として 300 文以上を検討する。日本語のみ、英語のみ、日英混合、句読点/記号、未知英単語、曖昧境界、長文を層化して採集する。必要数は事前の分散・検出力見積もりで確定する。
- **正解出力と責務区間はモデルの結果を見ずに事前アノテーション**する。表記揺れがある場合は許容表記を試験前に定義する。
- 開発セット、調整セット、最終 hold-out を文脈・語彙の漏洩が生じない単位で分割する。テスト結果を見た調整を hold-out で繰り返さない。
- 少なくとも一部を複数人で独立ラベル付けし、不一致率と裁定方法を記録する。
- 初期入力案 `pilot-corpus.jsonl` の `draft_expected_output` は**仮の期待値**であり、確定した正解ラベルではない。

## 4. 測定量と計算式

### 4.1 文字誤り率 CER（主要評価）

```text
CER = (S + D + I) / N
```

S: 置換、D: 削除、I: 挿入、N: 参照文字列の文字数。
各文の編集距離を合計して参照全文字数で割る（micro CER）。
Unicode の正規化（NFC 等）、句読点、英大文字/小文字、全角/半角の採点規則を事前に固定する。
CER は 1 を超える場合もある。完全一致率も併記する。

### 4.2 言語責務境界

入力 raw の **文字間位置**（先頭を 0 とする）で、日本語 / Literal が切り替わる箇所を
人手で標識する。Mozc 内部の漢字変換の単語境界とは区別する。

```text
P = TP / (TP + FP)
R = TP / (TP + FN)
F1 = 2PR / (P + R)
```

空集合・境界ゼロの事例は、集計仕様を事前に決める。
HardBoundary や句読点の扱いも両方式で共通にする。
候補辺のうちどれを「予測された責務境界」と呼ぶかを固定し、gold を見てから選ばない。

### 4.3 早期誤確定 / 遅延

```text
誤確定試行率 = 途中で不可逆な誤確定が1回以上あった試行数 / 全有効試行数
誤確定頻度   = 誤確定イベント合計 / 入力キー数 * 1000
確定遅延     = 対象区間の入力終了から正しい区間確定までの追加打鍵数
```

`CommitEvent` の総数は「誤確定数」ではない。時点別の gold を見て後戻り不能な
誤確定かを判定する必要がある。Undo/修正コストも別記するとよい。

### 4.4 パフォーマンス

- `Stopwatch` 等の単調時計で各打鍵処理の wall time を採取する。処理本体と描画の時間を分離する。
- 中央値、P95、P99、最大値、CPU使用率、ピークメモリ、Mozc問い合わせ回数を報告する。
- ウォームアップ・反復回数・外れ値扱い・Windows電源プランを固定し、同一PCで比較順序を交互/ランダム化する。
- `ExpandedEdgesThisStep` や `TotalExpandedEdges` は **計算量の代理指標**であり、処理時間(ms)ではない。

### 4.5 スコアを「信頼度」と呼ぶ場合の校正検証（未実施）

候補スコアを正解確率として利用したい場合、**まず確率としての意味を定義し、
開発セットのみで校正関数を学習する**必要がある。
現状の `mozcQuality` 等は主としてヒューリスティックなスコアなので、
値 0.98 を「98%の確率で正しい」とは解釈しない。

将来、確率予測 `p_i` が定義できた段階で、独立 hold-out 上の
正否ラベル `y_i ∈ {0,1}` と比較する。信頼度ビン `B_m` ごとに:

```text
ECE = Σ_m (|B_m| / N) × | mean(y_i in B_m) - mean(p_i in B_m) |
Brier score = (1/N) × Σ_i (p_i - y_i)^2
```

信頼度別の実測正解率・件数・信頼区間を reliability diagram に描く。
ECE はビン定義に依存するので、ビン数/境界を先に固定する。
**スコアの順位識別能力、確率校正、最終文字出力のCERは異なる概念**であり、
一つの指標だけで性能を主張しない。現時点でこの評価の実測値は存在しない。

## 5. 統計解析と採択条件

- 一次比較は、**同一の hold-out 文章集合**に対する `v0.6_mozc` と事前に選んだ基準方式の CER 差とする。
- `ΔCER = CER_baseline - CER_candidate`。正なら改善。
- 文章単位で対応関係を保持した paired bootstrap（例: 5,000 再標本、固定 seed）で 95% 信頼区間を算出する。
- ΔCER の95%区間下限が 0 より大きい場合、**その評価セットと条件で**改善を支持する証拠とする。統計的有意性と実用上の改善幅は別に報告する。
- 複数の方式間比較・カテゴリ分析は探索的と明記する。複数比較を正式な主張にするなら調整方法を事前規定する。
- 境界 F1・誤確定率・遅延は副次評価として、絶対値・差・区間推定・失敗例を併記する。
- 未接続、タイムアウト、クラッシュ、データ欠損は隠さず集計し、完了試行だけを恣意的に比較しない。
