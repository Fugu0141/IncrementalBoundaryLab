## 1. 何が技術的に良いか

1. **責務の分離**: `StreamHybridDecoder` は単一のかな変換器ではなく、辞書・音韻・英語島・コード構造・形態語尾の候補を一つの座標系に格納し、競合経路を探索する。`StreamHybridSession` は確定境界を分けて管理する。これは異種表記の混在に適した設計方向。
2. **接続可能な候補グラフ**: v1.2 は、`node.js` 候補自体は存在しても前に来る日本語経路がその開始点まで切れない問題を特定した。前段候補へ英語候補の開始点を伝播し、経路接続を改善している。単にスコアを増やすより本質的。
3. **曖昧さの可逆的保持**: 明示的な強い区切り以外では v1.3 は自動確定せず、代替経路と分析用トレースを維持。実IMEへ進む前段階として妥当。
4. **実験を定量化**: Claude が単独 C# 評価ハーネス・合成コーパス・失敗の切り分け・異常系・編集時の復元テストを追加したことは高評価。既存テストだけでは気づきにくい未知英語の破綻を可視化している。
5. **測定範囲の正直な記述**: 付属文書には Mozc 実機比較・盲検 holdout・TSF 性能は未測定と明記されている。

## 3. コード監査で発見した問題

- **誤った原因帰属**: `StreamHybridDecoder.cs` は `LanguageProfileScorer` を呼んでいない。現行 v1.3 の失敗をこの n-gram モデルの弱さで直接説明するのは誤り。同スコアラーを利用するのは旧 `EvidenceLatticeDecoder` など。
- **正解ラベル誤り**: `tests/BoundaryLab.Core.EvalHarness/AdversarialCorpus.cs` の `myunknownsite.comniarimasu` は、正解出力が `myunknownsite.comにあります` なので言語切替は `"myunknownsite.com".Length == 17`。コードの gold は `[20]` になっている。このバケットの boundary F1 はそのまま信頼できない。修正パッチを同梱。
- **候補生成と候補選択が混同されやすい**: `AddKanaRuns` の `TakeLast(4)` による候補の選別、候補始点ごとの `Take(12)`、ビーム幅6は正しい経路の存否に関わる。候補がなければ後段のスコアを上げても解決しない。
- **大文字情報の早期破棄**: `StreamHybridSession.Update` は `InputSyntax.Normalize` で ASCII を小文字化する。`IME` / `ime` 等の区別は以後原理的に不可能。
- **累積再デコード**: 未確定領域が伸びるたび `Process` -> `_decoder.Decode(active)` を毎文字実施。固定サイズのビーム/辺長でも、active全体を毎回調べれば累積処理量は理論上 `sum_{k=1}^n O(k)=O(n^2)`。将来的に永続的なビーム状態や差分更新が必要。
- **測定上の交絡**: 既知辞書語については実装辞書と gold が同根。辞書を覚えていることと未知入力への一般化は分けて評価すべき。変換結果の CER と候補再現率、境界F1、入力遅延は別の指標。

## 4. 新仮説 H1 — 辞書外の英単語も文字の並びの統計から候補化できるか

### 仮説

英単語の固定語尾のみで保護する v1.3 の `AddMorphologicalLatinIslands` より、独立した英語文字モデルと日本語ローマ字文字モデルの尤度差で**英語候補を追加する**方式のほうが、辞書外の英語候補 recall を高められる。ただし、それだけで正しい混在分割を確定できるとは仮定しない。

### 方法

- 英語学習資料: CMU Pronouncing Dictionary (`cmudict` Python パッケージ) の英単語型。評価対象54語と日本語の評価語を学習集合から除外。seed=20261010 の学習数は英語116,732語、日本語55語。
- 日本語学習資料: リポジトリ `Lexicon.cs` の日本語綴りから55語。検証15語、独立テスト15語、さらに元々辞書にない日本語の音韻19語。英語側の別の開発450語と合わせ、**開発集合だけで閾値選択**。
- モデル: 1〜3文字文脈の条件付き文字モデル (加算平滑化)。正規化平均対数尤度 `L_EN(w)-L_JA(w)` が閾値超なら可逆的な英語候補を追加。
- Baseline: 既存コードと同じ固定 suffix セット (`ology, tion, sion, ment, ness, able, ible, ese`)、長さ7〜24字。長い英文を分類する実験ではなく、限定された *候補生成* の比較。
- 英語54語: `Corpus.cs` の `EnOov`。gold は評価器の出力から学習しない。混在入力は `日本語プレフィクス + 未知英語 + 助詞` で機械的に作成し、その結合位置を gold とする。

### 実測結果 (seed=20261010)

| 候補の作り方 | 単独の未知英語54語に正しい候補 | 日本語34語の英語誤判定 | 混在文字列で gold に一致する候補位置 | 混在正例54件の候補総数 |
|---|---:|---:|---:|---:|
| v1.3型の固定語尾パターン | 5/54 (9.3%) | 0/34 | 5/54 | 53 |
| 文字モデル | 32/54 (59.3%) | 0/34 | 30/54 | 166 |
| 文字モデル + 固定語尾の両候補 | 34/54 (63.0%) | 0/34 | 32/54 | 207 |

文字モデル単独と固定語尾パターン間の54例の対比較（新方式のみ検出29語、旧方式のみ検出2語）は exact McNemar 二側 p≈4.63×10^-7。ただし英語単語は独立な無作為標本ではなく、研究用の選択語彙なので、この p 値を一般的な日本語IMEの改善の有意性と見なしてはいけない。

単独検出34/54の Wilson 95%区間は約49.6〜74.6%。日本語誤判定0/34でも、Wilson 95%上限は約10.2%。誤判定しないことを証明したわけではない。

**評価**: H1 の「固定語尾だけより広い英語候補を生成できる」は本コーパスで支持。閾値選択が日本語15語の小さい開発集合に依存し、誤候補と提案数が大きく変動するため、「精度を保って実際のIME変換を改善できる」は**未立証**。特に seed 20261013 は和文だけの混在34件中13件に不適切な英語候補が現れた。片側の候補再現率のみを伸ばす設計は危険。

### 個別事例

- `customer`, `monitor`, `strategy` は seed=20261010 の文字モデルで英語候補として検出。
- `japanese` は固定語尾 `-ese` なら候補化できるが、保守的閾値の文字モデル単独では候補化できない。補完関係あり。
- `tokyo`, `ime`, `node` は保守的文字モデルでは英語候補にならない。これを機械的に英語と断定することは、そもそも入力意図の観測なしでは不可能。

## 5. 原理的に解決不能な曖昧性と新仮説 H2

**主張**: 完全に同一の打鍵系列が日本語ローマ字と英語リテラル両方を意味しうる場合、追加の観測がなければ決定的変換器は両意図を同時に満たせない。

**証明**: `f("tokyo")` を一意に決める任意の決定的関数 `f` を考える。一方の利用者が「ときょ」（未確定日本語）を意図し、他方が文字列 `tokyo` を意図した場合、期待される二つの結果は異なる。同じ入力値に対する `f` の出力は一つだけなので、少なくともどちらかを誤る。この事実はより大きなモデルや辞書でも解消しない。確率分布で最頻解を選ぶか、ユーザーの明示的な意図 (Latin lock, case, 修正履歴, IMEモード) を追加で観測する必要がある。

**H2 (次の実装実験)**: 原文の大文字・小文字を保持し、ASCII領域に可逆的な `LatinIntent` の証拠を追加する。`IME` のような明示大文字、ユーザーがLatin固定した区間、コード記号のまとまりは強く優先し、`ime` という小文字入力では日本語寄りのデフォルトを残す。機能テストでは同一文字列の大文字/小文字の差、後方修正、勝手な確定を検証する。

## 6. 次の実装ロードマップ

1. 研究用評価の修正: gold位置 `[20]` を計算値 `"myunknownsite.com".Length` に置き換え、C#ハーネスを改めて実行。研究対象のブランチとアルゴリズム名を必ず出力する。
2. 候補再現率診断を C# に追加: 全候補の正解経路が **候補生成前から存在しない**か、候補12本への枝刈りで脱落するか、ビーム6の経路探索で脱落するか、順位付けで選ばれないかを別カウンタで追跡。
3. 文字モデルを**確定器ではなく英語候補提案器**として C# に追加。英語モデルのデータライセンスと更新方法を確認し、固定語尾方式との ablation 比較を実施。日本語のみの誤変換増加をブロックする。
4. 「日本語を基本にする」制約をそのまま生かす。強い明示意図以外は複数経路を保持し、短い日本語助詞の辞書ヒットは、英語候補区間の内部では単独では強い確証にしない。
5. 逐次入力・削除・モード変更の計測を追加。入力遅延は Windows の p50/p95/p99、変換安定性は訂正回数・不当確定回数、精度は独立の実際の文章と人手確定goldで測定する。1キーごとに全長を再計算する構造から段階的に脱却する。
